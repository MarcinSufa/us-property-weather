## Decisions already made by the conductor

1. The provider sends only the zip code to Weatherstack (`query=<zipCode>`), so "the unknown-location address of the tests" is identified by its zip code. Use zip code `00000` for it. The stub answers `GET /current` whose `query` parameter is that zip with `current-unknown.json` and HTTP 400, every other `/current` with `current-85268.json` and HTTP 200, both read from `apps/api/src/weather/fixtures/` at request time or start, never copied. `GET /__calls` returns JSON `{ "calls": <number> }`, the number of `/current` requests served, both kinds counted. Any other path or method: 404. The stub listens on `127.0.0.1` on a port taken from its environment; choose a port that is not 4000 or 5173 and define it once.
2. The three servers of `webServer`, each with `reuseExistingServer: false`: the stub and the API are started with `node` directly (no `npm run`, no `--env-file`); the API as `node src/main.ts` with `cwd` at `apps/api` and the whole configuration in `env` exactly as the brief lists it. For the web dev server prefer starting Vite with `node` on its bin file too, if that works from `apps/web`, so no `npm` parent is left behind on Windows; otherwise `npm run dev --workspace=apps/web`. Give each server a readiness `url` (the stub's `/__calls`, the web root) or `port` that proves it listens. The API has no health route: a GET of `http://localhost:4000/graphql?query=%7B__typename%7D` answers 200.
3. The temporary database: a file inside a fresh directory made with `mkdtemp` under `os.tmpdir()`, removed when the run ends. Three facts you must design for, because each one broke a naive version of this elsewhere: (a) Playwright loads the config file in the runner process and again in every worker process, so a `mkdtemp` at module top level makes several directories unless the path is handed down (for example through an environment variable that the runner sets once and the workers inherit); (b) on Windows Playwright force-kills the servers, so the API never runs its own shutdown, and SQLite keeps the file locked until that kill: `globalTeardown` runs BEFORE the servers are stopped, so removing the directory there fails with `EBUSY` on Windows; (c) the removal must therefore happen after the servers are gone, in the runner process only, and must not throw if the directory is already gone. A `process.on('exit', ...)` handler registered in the runner process with a synchronous `rmSync(dir, { recursive: true, force: true, maxRetries: ... })` is one way that fits; use another if you can show it is correct on Windows and Linux. The conductor checks after each run that no directory of the suite is left in the temporary folder, so give the directory a recognisable prefix (`covertree-e2e-`).
4. The suite must not depend on the internet. The web page asks Google Fonts for two font families and the weather card loads its icon from the weather provider's image host. Abort every browser request whose host is not `localhost` or `127.0.0.1` (one `route` on the context or page, set up once for all tests), so a run in CI without those hosts behaves the same. The remote icon and the fonts are out of scope: assert nothing about them.
5. `playwright.config.ts`: Chromium only, `workers: 1`, `fullyParallel: false`, no retries, `forbidOnly` in CI, `baseURL` `http://localhost:5173`, reporter `list` plus `html` with `open: 'never'` (its folder `e2e/playwright-report/` and `e2e/test-results/` are already ignored by git), trace `retain-on-failure`. The stories share one database and run in file order, each building on what the earlier ones created; say so with `test.describe.configure({ mode: 'serial' })` so a failure stops the rest instead of reporting misleading follow-up failures.
6. Root `package.json`, the `typecheck` line, exactly: `"typecheck": "npm run typecheck --workspace=apps/api && npm run typecheck --workspace=apps/web && npm run typecheck --workspace=e2e",`. In `e2e/package.json` add `"typecheck": "tsc --noEmit -p tsconfig.json"`. `e2e/tsconfig.json` extends `../tsconfig.base.json` with `module` and `moduleResolution` `NodeNext` and `types: ["node"]`, and includes every `.ts` file of `e2e/`. ESLint runs typed rules through `projectService`, so every `.ts` file under `e2e/` must be covered by that tsconfig.
7. `.github/workflows/ci.yml`: as the brief says. The newest major versions that exist today, checked by the conductor against the GitHub API on 2026-10-13: `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`. One job on `ubuntu-latest`, `permissions: contents: read` at workflow level, `node-version: 24` with `cache: npm`, then in this order `npm ci`, `npm run verify`, `npx playwright install --with-deps chromium`, `npm run e2e`, and the upload of `e2e/playwright-report/` with `if: ${{ failure() }}` (plain `failure()` is fine) and a short retention. No secret, no `env` with a key. Triggers: `push` and `pull_request`. Add a `concurrency` group only if you can state why; otherwise leave it out.

## The stories (`e2e/stories.spec.ts`, one file unless one per story clearly reads better)

Every test name starts with the id of the criterion from `docs/SPEC.md` that it proves in the browser; pick the UI criterion of the story (the table "User story coverage" at the end of `docs/SPEC.md` maps stories to ids). Where a test proves two criteria, start with the main one and name the other after it. Locators by role and accessible name or by label, as in the web tests (`apps/web/src/pages/*.test.tsx` show the names in use). Never by class or test id. No `waitForTimeout`, no fixed sleeps: web-first assertions only.

The stories and what each must assert, from the brief plus four browser facts the `web` slice could not prove in its test DOM:

1. Create: at the start the stub count is 0. Fill the form, submit, land on `/properties/<id>` of the new property with its heading and the weather card ("Weather at creation") showing values of the success fixture. The stub count is 1.
2. Create with an unknown location (zip `00000`): the alert of `LOCATION_NOT_FOUND` is shown with its sentence, the four typed values are still in the form, the URL is still the form, and the list afterwards does not contain that street.
3. Create with input the browser lets through but the server rejects (a street of spaces passes the native `required`): the server's field error is shown under its field. Prove "under its field" by the accessible relation, not by position: the Street input is invalid (`aria-invalid`) and its accessible description contains the server's message (Playwright `toHaveAccessibleDescription` or `toHaveAccessibleErrorMessage`, whichever the markup of `apps/web/src/components/FieldErrors.tsx` supports), and focus is on the Street input. The stub count did not change, because validation comes before the weather lookup.
4. List: after creating the properties the later stories need (at least three, in at least two cities, two states and two zip codes, created through the form, each create counted), the rows show street, city, state, zip code and the weather summary of the fixture.
5. Filter: by city typed in another letter case, by state, by zip code. After each, only the matching rows are listed, the URL carries the filter (`city`, `state`, `zip` parameters), and `page.reload()` shows the same rows and the same values in the filter form.
6. Sort: newest first by default (the order of the rows is the reverse of creation), oldest first when chosen; the URL carries `sort=oldest` and a reload keeps it.
7. Detail: reached by clicking the street link of a list row; shows the address, latitude and longitude of the fixture, and the weather card.
8. Delete, with the dialog facts inside this story: open the dialog from a row's delete button. Then assert: the dialog is open as a modal (for example `dialog:modal` matched through `locator.evaluate((element) => element.matches(':modal'))` on the role-located dialog, and a control behind it cannot be reached: the page content is inert to clicks), it names the street, and focus is on "Cancel". Press Escape: the dialog is closed, the row is still there, and focus is back on the delete button that opened it. Open it again, click "Cancel": closed, row still there, focus back on the same button. Open it again and confirm: the row is gone, the count line reflects it, and opening the deleted property's detail URL shows "Property not found".
9. The weather proof, last: after all of the above the stub count equals the number of creates that reached the weather lookup (every successful create plus the unknown-location one, not the invalid one) and nothing more. Keep the expected number as a running count that each create increments at the place it is sent, not a literal written at the end, and read the stub through Playwright's `request` fixture or `fetch` at the stub's `/__calls`. Also assert the count before and after one list load, one filter, one sort change, one detail page and the delete inside their own stories, so a failure names the action that reached the weather service.

If the app does something else than a story expects, first check the app's source to see whether the expectation or the app is wrong. If the app is wrong against `docs/SPEC.md` or `docs/plan.md` section 10, leave the assertion as it is and report it.
